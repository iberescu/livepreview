# psd-mockup-service

An HTTP API that puts an uploaded image into a named **smart object** of a PSD template and
returns the rendered mockup as a web image (WebP, JPEG or PNG). It does what a Photoshop
"Replace Contents → Save for Web" droplet does, without Photoshop: no UI, no GPU, many requests
in parallel, and smaller outputs cost less. Rendering uses
[PhotoCraft](https://github.com/storytold/photocraft)'s Rust engine on the CPU; the service is
built in Docker against a pinned PhotoCraft commit.

## Run

```sh
docker compose up -d --build        # first build ~3 min, rebuilds ~1 min
curl localhost:8080/templates
```

Templates are the `.psd` / `.psb` files in the folder mounted at `/data/psds` (`PSD_HOST_DIR` in
`.env`, default `./psds`; subfolders are fine). A template's id is its path without the
extension: `shirts/front.psd` → `shirts/front`. New and changed files are picked up the next time
they're used; no restart needed. The service answers immediately after start and parses templates
in the background; a request for a template still loading waits for it.

## Test page

`http://localhost:8080/` is a test page: every template with three example designs made at its
placeholder's exact size (`examples/`, generated by `python examples/generate.py` with
PhotoCraft's CLI), a smart-object picker, scale/format/fit options, a file input for your own
image, and a Render button that shows the result with the server's timings. The page also works
opened as a file (it then talks to `localhost:8080`; the API allows any origin).

## API

### `GET /templates`, `GET /templates/{id}`
Every template with its smart objects:

```json
{"id": "T-shirt_landscape_white", "width": 2500, "height": 1666, "mode": "Rgb", "bits": 8,
 "smart_objects": [
   {"name": "< T-Shirt - Place Your Design Here", "layer_id": 28, "width": 2593, "height": 2873,
    "visible": true, "placeholder_coverage": 1.0, "instances": 1},
   {"name": "layer", "layer_id": 53, "width": 12992, "height": 2716, "placeholder_coverage": 0.29,
    "filters": ["Displace (Photoshop; implemented by this service)"], "instances": 0}]}
```

- `width`/`height`: pixel size of the smart object's contents. The upload is fitted to it.
- `placeholder_coverage`: how opaque the placeholder is. **1.0 means the smart object is a
  full-surface texture** (in the T-shirt template it is the whole shirt), so send an opaque image
  of the same aspect ratio, or pass `design_background`; a transparent design would leave holes
  in the shirt, exactly as it does in Photoshop. Low values mean a print-area placeholder.
- `instances`: other smart objects sharing the same contents. Photoshop replaces them together;
  so does the service (`instances=false` to replace only the named one).
- `opacity`: mockups often keep an opacity-0 "replace me" layer. If it has `instances`, those
  do the visible work and replacing it is the right move (the coffee die-cut's `Replace
  Artwork`); if it has none, replacing it changes nothing and the visible smart object is the
  one to target (the bag's `layer`).
- `filters` / `warp`: the smart filters and warp applied to the contents, and how they're rendered.

### `POST /render`
`multipart/form-data` with an `image` file field, or the raw image as the body with the
parameters in the query string.

| param | default | |
|---|---|---|
| `template` | required | template id |
| `smart_object` | required* | smart object layer name (exact, then case-insensitive) |
| `layer_id` | | *or* Photoshop's layer id (what a recorded action's `LyrI` holds) |
| `format` | `webp` | `webp`, `jpeg`, `png` (the droplet's PNG-24 equivalent is `png`) |
| `quality` | `85` | 1–100 for JPEG / lossy WebP; `lossless=true` for lossless WebP |
| `scale` | `100` | output size as a percentage of the document, like Save for Web's Percent (`25`, or `0.25`) |
| `width`, `height` | document size | alternatively, maximum output size; aspect kept, never upscaled |
| `fit` | `contain` | `contain` (whole design visible, rest transparent), `cover` (fill, crop centred), `fill` (stretch) |
| `design_background` | none | hex colour for the transparent parts of the fitted design, e.g. `#ffffff` for a white shirt |
| `background` | none (white for JPEG) | flatten the *output's* transparency onto a colour |
| `instances` | `true` | also replace smart objects sharing the contents |

```sh
# multipart (note --form-string: curl reads a plain -F value starting with "<" from a file)
curl --form-string template=T-shirt_landscape_white \
     --form-string "smart_object=< T-Shirt - Place Your Design Here" \
     --form-string scale=50 --form-string design_background=#ffffff \
     -F image=@design.png localhost:8080/render -o mockup.webp

# raw body + query string, by layer id, capped at 800 px wide
curl "localhost:8080/render?template=Bottle_landscape_red&layer_id=2743&format=png&width=800" \
     --data-binary @label.png -o mockup.png
```

The body is the image, with headers `x-image-width`, `x-image-height`, `x-replaced-layers`,
`x-render-scale` (the fraction of the document the composite was rendered at, see below) and
`server-timing` (milliseconds per stage). Errors are JSON `{"error": "…"}` with status
400/404/422; an unknown smart object lists the available names.

Uploads can be anything PhotoCraft opens: PNG, JPEG, WebP, TIFF, GIF, BMP, HEIC, AVIF, EXR,
SVG, PSD/PSB (flattened), camera raw; 8/16/32-bit; EXIF orientation applied; embedded RGB, gray
and CMYK profiles converted to the document's colour.

### `GET /preview?template=…&source=photoshop|photocraft`
The template as Photoshop saved it (its flattened image) or as this service composites it with
nothing replaced; same output options (`scale`, `width`, `format`…). Useful to compare the two.

## Output size and cost

Asking for a smaller image makes the render cheaper, not just the file: the composite happens
on a downscaled copy of the template (1/2, 1/4 or 1/8 of the document, the smallest that still
covers the requested size), then the result is resampled to the exact size asked for. The copies
are built once per template on first use (~150 ms each) and kept in memory; they keep every
layer's Photoshop pixels (resampled), scale layer effects as Photoshop's "Scale Styles" does, and
scale smart object placements, so nothing is re-rendered from source. The upload is likewise
fitted only to the resolution the placement needs: a 13 000-pixel-wide label placeholder placed
at 7% of its size is fitted at 14%, not 100%.

Measured against Photoshop's own flattened image, resampled to the same size (mean absolute
difference, 0–255):

| template | 100% | 50% | 25% |
|---|---|---|---|
| T-shirt | 0.13 | 0.34 | 0.49 |
| hoodie | 0.00 | 1.24 | 0.97 |
| bottle (16-bit) | 0.00 | 0.18 | 0.30 |

## Fidelity

`mockup-server check <template> [out-dir]` (run inside the container:
`docker compose run --rm mockup check T-shirt_landscape_white`) re-renders each smart object
from its own contents and compares it with the pixels Photoshop saved for that layer, then
compares the whole composite with Photoshop's flattened image. Measured on the three supplied
templates (mean absolute difference, 0–255):

| template | smart object | layer re-render vs Photoshop | whole composite vs Photoshop |
|---|---|---|---|
| T-shirt (2500×1666) | design (2 instances) | 0.06 | 0.13 |
| | design copy (Gaussian Blur + Ripple) | 4.2 (Ripple skipped) | |
| | neck label (Displace, Color Overlay) | shape 4.1 | |
| hoodie (4500×3045) | print (Displace, perspective) | 3.0 (45 without Displace) | 0.00 |
| bottle (3000×2100, 16-bit) | label (Arc Lower warp, Color Overlay) | 3.1 (111 with PhotoCraft's own preset formula) | 0.00 |
| bag (2500×1668) | design | 0.7 | 0.01 |
| canvas (4500×3000) | artwork | 1.5 | 0.63 |
| coffee die-cut (1536×1024) | artwork → stencil hole + cocoa (3 instances) | 4.3–5.5 (Ripple skipped) | 0.70 |
| roll of stickers (4056×3001) | 6 sticker instances + inside, all with custom warps | 0.2–0.9 shape (16–190 as PhotoCraft reads them) | 1.14 |

What makes those numbers:

- **Compositing**, layer effects and blend modes are PhotoCraft's, and match Photoshop to
  within rounding on these files (every layer keeps Photoshop's pixels except the replaced one).
- **Displace** (Photoshop's filter, which PhotoCraft doesn't implement) is implemented here from
  the map Photoshop embeds in the PSD (`src/displace.rs`); its direction, area and sampling were
  chosen by comparing with Photoshop's render.
- **Custom warps** (Edit › Transform › Warp meshes stored in the PSD): Photoshop's transform
  quad for a warped layer is where the bounding box of the warp's control net lands, not where
  the original box would. PhotoCraft maps the original box, which bends stickers too little or
  folds them wrongly; the service maps the control net's extent onto the box instead, verified
  against Photoshop's pixels at load (`warp.fit` shows before/after; the fix is only kept when
  it matches better).
- **Preset warps** (Arc, Arc Lower, Flag, …): the PSD stores only the preset's name and bend,
  and Photoshop's formulas are undocumented, so the service recovers the actual Bezier mesh by
  fitting PhotoCraft's render of the original contents to Photoshop's pixels (`src/meshfit.rs`),
  once per template (~7 s, cached in `./cache`). `warp.fit` in `/templates` reports the
  before/after error. The surest alternative: in Photoshop, set the smart object's warp preset
  to **Custom** and save; the PSD then holds the exact mesh and no fitting is needed.
- Not implemented: Photoshop filters other than Displace (Ripple here; listed as "skipped" in
  `filters`), and the colour profile of *gray* placeholder files (irrelevant for replacements).

## Performance (32-core machine, Docker Desktop, warm)

| template | upload | 100% | 50% | 25% |
|---|---|---|---|---|
| T-shirt 2500×1666 | 2593×2873 PNG, 2 instances replaced | 480 ms | 210 ms | 130 ms |
| hoodie 4500×3045 | 35-megapixel PNG | 1000 ms | 520 ms | 390 ms |
| bottle 3000×2100 16-bit | 35-megapixel PNG | 520 ms | 400 ms | 370 ms |

Decoding the upload is the floor that doesn't shrink with the output (~260 ms of the hoodie and
bottle times is the 35-megapixel test upload; a normal-size upload decodes in 10–60 ms). The
first request for a template also waits for it to load (2–9 s).

Renders run on blocking worker threads, each itself parallel; `MAX_CONCURRENT_RENDERS` caps how
many run at once (extra requests queue; the wait shows as `queue` in `server-timing`). 96 renders
of a 1600×1200 template at 16 concurrent clients took 3.6 s.

## How a render works

1. The upload is decoded with PhotoCraft (EXIF orientation, ICC → sRGB), fitted to the smart
   object's contents at the resolution its placement needs, optionally filled with
   `design_background`, and converted to the document's colour profile and pixel format.
2. It goes through the smart object's own placement: transform, perspective, warp (the stored or
   recovered mesh), then its smart filters (PhotoCraft's, plus Displace). The template document
   (or its downscaled copy) is a copy-on-write clone, so the stored template is never touched
   and requests share its tiles.
3. The document is composited in bands across all cores (effects, blend modes, masks, clipping),
   converted to sRGB, resampled to the requested size (SIMD Lanczos3) and encoded (libwebp,
   JPEG, PNG).

## Files

- `src/templates.rs`: the PSD store (scan, parse, cache, reload on change), warp preparation,
  downscaled copies
- `src/scale.rs`: downscaling a document, and fitting uploads at the resolution a placement needs
- `src/render.rs`: upload decoding, fitting, placement, composite, encode
- `src/displace.rs`, `src/filters.rs`: Photoshop's Displace, and the smart filter stack
- `src/meshfit.rs`: recovering preset warp meshes from Photoshop's render
- `src/check.rs`: the fidelity check (`mockup-server check`)
- `src/main.rs`: the HTTP API (axum)
- `Dockerfile`: fetches PhotoCraft at `PHOTOCRAFT_REF` and builds the service inside its workspace
